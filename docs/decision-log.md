# Architecture Decision Records (ADR)

> **Status:** All Records Active & Binding  
> **Clean Restart Baseline Version:** 1.0

---

## ADR-001: Abandonment of Supabase in Favor of Native PostgreSQL 16+ & ASP.NET Core
- **Context:** Previous architecture utilized Supabase for Auth, Realtime, and direct client queries, leading to fragmented security boundaries, lack of transactional guarantees, and leaky multitenancy.
- **Decision:** Remove all Supabase dependencies completely. Adopt native PostgreSQL 16+ with Entity Framework Core 10, ASP.NET Core Identity, and custom cookie session management.
- **Consequences:** Direct full control over transactional boundaries, append-only stock ledgers, strict database constraints, and complete self-hosted portability.

---

## ADR-002: Modular Monolith Architecture (Clean Architecture Pattern)
- **Context:** Avoid microservice distribution overhead while maintaining strict domain boundaries.
- **Decision:** Structure the backend into four discrete layers:
  1. `Inventory.Domain` (Pure business entities, value objects, exceptions, no external dependencies).
  2. `Inventory.Application` (Use cases, commands, queries, DTOs, interfaces, validation).
  3. `Inventory.Infrastructure` (EF Core DbContext, PostgreSQL persistence, Identity, SMS abstraction, file storage).
  4. `Inventory.Api` (Thin controllers, HTTP middlewares, authentication/authorization handlers, swagger).
- **Consequences:** Highly testable, clean dependency direction (`Api` → `Application` → `Domain` ← `Infrastructure`).

---

## ADR-003: Warehouse-Only Inventory Ownership
- **Context:** Prior versions attempted to track inventory balances and in-transit goods across restaurants, resulting in sync errors and accounting contradictions.
- **Decision:** Warehouses are the **sole** entities that hold inventory. Restaurants have supply requests, confirmed receipts, and consumption history, but **never** a stock balance or in-transit balance.
- **Consequences:** Eliminates double-counting; simplifies inventory valuation; eliminates phantom in-transit balances.

---

## ADR-004: Stock Deduction Timing: Receipt Confirmation (Not Dispatch)
- **Context:** If dispatch deducted stock, unfulfilled or damaged in-transit items caused stock leaks and required complex reverse movements.
- **Decision:** Dispatching a supply from a warehouse does **not** change stock quantities. Warehouse stock is deducted **only** when the Restaurant Supervisor confirms actual received quantities.
- **Consequences:** Stock deductions reflect physical reality at the restaurant dock; discrepancies are recorded cleanly at confirmation time.

---

## ADR-005: Retirement of the "Accountant" Product Role
- **Context:** The `Accountant` role created permission ambiguities and overlapping operational/financial responsibilities.
- **Decision:** The `Accountant` role is permanently retired. The 5 approved product roles are:
  1. `Owner` (Full business & financial authority).
  2. `Admin` (Operational administrator; denied financial data & audit logs).
  3. `Warehouse Staff` (Warehouse logistics; scoped to assigned warehouses).
  4. `Restaurant Supervisor` (Branch ordering/confirming; scoped to assigned restaurants).
  5. `User` (Base user; explicit permission grants only).

---

## ADR-006: Server-Side Financial Data and Audit Log Denial for Admin
- **Context:** Business requirements mandate that operational administrators must not inspect profit margins, item purchase costs, inventory valuations, or company audit logs.
- **Decision:** Implement **Role Denial** at the ASP.NET Core authorization and DTO projection layers. Any query executed by an `Admin` strips financial columns (`unitCost`, `totalCost`, `valuation`) and forbids access to `/api/v1/audit` (returns HTTP 403 Forbidden), regardless of any ad-hoc user permission claims.

---

## ADR-007: Elimination of Barcode and English Item/Unit/Category Names
- **Context:** The platform is an enterprise Arabic-first management system. Storing unused barcode and English name fields introduced dead schema, validation clutter, and sync overhead.
- **Decision:** Remove `barcode`, `nameEnglish` / `name_en` from database schemas, domain entities, DTOs, API endpoints, and frontend forms.
- **Consequences:** Clean schema, focused Arabic UI, no dead input fields.

---

## ADR-008: Server-Generated Item Codes & Document Numbers
- **Context:** Client-entered item codes or fragile `SELECT MAX(code) + 1` queries caused duplicate key errors during concurrent additions.
- **Decision:** All Item Codes (`generatedCode`) and Document Numbers (`documentNumber`) are generated by server-side sequence services using PostgreSQL sequences or atomic database transaction locks. Frontend displays item codes as read-only.

---

## ADR-009: Costing Model: Weighted Average Cost (WAC) via Actual Receipts
- **Context:** A static, manually editable item purchase price creates conflicting sources of truth against actual purchasing invoices.
- **Decision:** Item costs are derived strictly from posted incoming goods receipts using Weighted Average Costing (`decimal(18,4)` precision). Manual purchase price editing on Item master data is forbidden.

---

## ADR-010: Authentication via Mobile Number + Password and Secure Cookie Sessions
- **Context:** Restaurant workers and supervisors operate primarily with mobile numbers; email-based auth is impractical in this operational domain. Storing JWTs in `localStorage` exposes systems to XSS token theft.
- **Decision:** Authentication uses Mobile Number + Password. Sessions are managed via secure, HttpOnly, SameSite=Strict cookies. Mutating requests enforce CSRF anti-forgery tokens. Passwords resets require rate-limited OTP SMS verification.

---

## ADR-011: Frontend Architecture: Next.js 16 (App Router), TypeScript, Tailwind CSS
- **Context:** Need an enterprise-grade, high-performance, RTL-native web application with low cognitive load and zero template bloat.
- **Decision:** Next.js 16 with TypeScript and Tailwind CSS. Design language: Swiss-inspired enterprise minimalism with `Noto Sans Arabic` typography. Centralized API client in `src/lib/api-client.ts`. Strict separation between UI components, API calls, and business logic.

---

# Reconciliation Amendment — ADR-012 … ADR-026

> The following records were produced by the Clean-Restart specification reconciliation pass. Each resolves a conflict or fills a gap catalogued in `docs/32-specification-conflict-register.md`. All are **Active & Binding**. None reopens a FINAL business invariant.

---

## ADR-012: Financial Visibility Is Owner-Only and Non-Grantable
- **Resolves:** CR-010, CR-011.
- **Context:** `07 §1.3` masked financial fields for three roles and omitted `User`, while `15 §2` masked them for every non-Owner. Separately, `03` published `costs:view` and `valuation:view` as ordinary grantable permissions — permissions that, under `15`, could never take effect. A grantable permission with no effect is a security trap: an administrator would believe they had delegated cost visibility.
- **Decision:** Financial visibility (`unitCost`, `totalCost`, `averageUnitCost`, valuation, any cost-bearing report) is available **exclusively to the `Owner` role**, unconditionally, for every other role including `User`. The permission codes `costs:view` and `valuation:view` are marked `NON_GRANTABLE`: they document Owner capability and can never be assigned to a user. The same applies to `audit:view` and `audit:export`.
- **Consequences:** `07 §1.3` is corrected. The permission-assignment UI never lists non-grantable codes. An attempt to grant one returns `400 NON_GRANTABLE_PERMISSION`.

## ADR-013: The Activity Monitor Is Owner-Only With No Grant Path
- **Resolves:** CR-012.
- **Context:** `14 §3` described the Activity Monitor audience as "Owner Only (Admin restricted unless granted)", directly contradicting the inviolable rule that Admin has no audit visibility.
- **Decision:** The Activity Monitor is a derived read-model over `audit_logs` and inherits the audit log's access rule exactly: `Owner` only, no grant path, HTTP 403 for everyone else.
- **Consequences:** `14 §3` corrected. One authorization policy governs both `/api/v1/audit` and the Activity Monitor.

## ADR-014: Exactly One Product Role Per User
- **Resolves:** CR-013.
- **Context:** `user_roles` is a many-to-many join, yet every authorization sample in `03`, `09`, and `15` reads a singular `user.Role`. With two roles assigned, Role Denial has no defined subject: a user holding both `Admin` and `Owner` would be simultaneously denied and permitted cost visibility.
- **Decision:** A user holds **exactly one** of the five product roles. Enforced by `UNIQUE (user_id)` on `user_roles` and by the application service. Fine-grained variation is expressed through `user_permissions` and data scopes, never through multiple roles.
- **Consequences:** Role Denial is unambiguous. `/api/v1/account/me` returns a single `role` value. The `user_roles` table is retained (rather than a `users.role_id` column) so that role assignment history remains a first-class auditable event.

## ADR-015: Operational Authority Is Separable From Financial Visibility
- **Resolves:** CR-015.
- **Context:** `Admin` holds `receiving:reverse`. Reversing a posted receiving order necessarily recomputes Weighted Average Cost — a financial computation — for a role forbidden to see costs.
- **Decision:** An `Admin` may **trigger** operations whose server-side effects are financial. The server performs the computation; the response projection returns no cost field, and the audit entry records the computation for `Owner` review. Authority over an operation and visibility of its financial output are independent concerns.
- **Consequences:** Applies equally to stock-count approval and receiving verification. No operational workflow is blocked by financial lockdown, and no financial figure crosses the wire to a non-Owner.

## ADR-016: Composite Tenant-Consistent Foreign Keys
- **Resolves:** CR-016, CR-065.
- **Context:** Every foreign key in `06` is single-column. Nothing at the database level prevents a `supply_request` in Company A from referencing a `restaurant` in Company B, or a user in Company A from being scoped to Company B's warehouse. EF Core global query filters mitigate this in application code, but a filter bypass, a raw SQL path, or `IgnoreQueryFilters()` would silently create cross-tenant data.
- **Decision:** Every tenant-scoped table declares `UNIQUE (company_id, id)`, and every foreign key between tenant-scoped tables is **composite** on `(company_id, <fk>)`. Tenant isolation becomes a database invariant rather than an application convention.
- **Consequences:** Cross-tenant references are physically impossible. Full DDL in `docs/29`.

## ADR-017: Fulfilment and Dispatch Are Two Distinct Business Acts
- **Resolves:** CR-020, CR-021.
- **Context:** `07` exposed both `POST /supply-requests/{id}/fulfill` ("creates a Supply / Dispatch") and `POST /supplies/{id}/dispatch`. Either the second was meaningless, or the `Supply` had an undocumented state before dispatch.
- **Decision:** Fulfilment creates a `Supply` in state **`Prepared`** (`قيد التجهيز`): the warehouse has decided the quantities and picked the goods. Dispatch transitions `Prepared → Dispatched`: the goods have physically left. The canonical `Supply` status set is `Prepared`, `Dispatched`, `Confirmed`, `ConfirmedWithDiscrepancy`, `RejectedAtDelivery`, `Cancelled`. `Discrepancy` is **not** a status.
- **Consequences:** Neither transition touches stock. Both are separately audited and separately timestamped, so "picked but not shipped" is visible on the warehouse dashboard. `Cancelled` is reachable only from `Prepared`.

## ADR-018: In-Transit Quantity Is Derived, Never Stored
- **Resolves:** CR-030.
- **Context:** Because dispatch does not deduct (ADR-004), goods on a truck remain in the warehouse balance. A physical count performed during transit therefore finds a shortfall, and approving that count would post a spurious `PHYSICAL_ADJUSTMENT` destroying real inventory value. This is the principal consequence of ADR-004 and was entirely unspecified.
- **Decision:** A read-only figure `قيد النقل` is **computed on demand** as the sum of `dispatched_base_quantity` over `supply_items` whose parent `Supply` is in state `Dispatched`. It is:
  - never persisted as a balance row;
  - always attributed to the **warehouse**, never to a restaurant — so the no-restaurant-inventory invariant is untouched;
  - displayed on warehouse stock screens and on the stock-count screen;
  - subtracted from the expected physical figure during a count, so the counter reconciles against goods actually on the shelf.
- **Consequences:** Stock counts are correct during transit. `docs/29` defines the query and its supporting index. No new table, no new balance, no restaurant inventory.

## ADR-019: Dispatch Advises on Stock; It Never Reserves
- **Resolves:** CR-031.
- **Context:** Dispatch performs no stock check, so a warehouse can dispatch more than it holds. The failure surfaces hours later at the restaurant dock as `INSUFFICIENT_STOCK`, leaving a supervisor holding goods they cannot confirm.
- **Decision:** Dispatch computes `available = quantity − inTransit` and **warns** the dispatcher when a line exceeds it. The warning does not block, and no reservation is created — reservations would reintroduce a phantom balance, which ADR-003 forbids. If confirmation later fails on stock, the supply stays `Dispatched` and the resolution path is an `Owner`/`Admin`-approved `PHYSICAL_ADJUSTMENT` establishing the true balance, after which confirmation succeeds.
- **Consequences:** The physical world remains the source of truth. Documented failure path in `docs/30`.

## ADR-020: Weighted Average Cost Changes Only on Inbound Movements
- **Resolves:** CR-032, CR-033.
- **Context:** No document stated what happens to `average_unit_cost` when stock leaves.
- **Decision:** Under Weighted Average Costing:
  - `OPENING_BALANCE`, `INCOMING_POSTED` — recompute the WAC by the standard formula.
  - `INCOMING_RECONCILIATION` — reverse value at **the originating receiving line's `unit_cost`**, not at the current WAC, because the movement corrects that specific posting. Any other choice leaks cost between receipts.
  - `RESTAURANT_RECEIPT_CONFIRMED` and `PHYSICAL_ADJUSTMENT` — value the movement at the **current WAC** and leave the WAC **unchanged**.
- **Consequences:** `stock_ledger.unit_cost` is populated for every movement type, but only inbound types alter `stock_balances.average_unit_cost`. Unit-testable in isolation.

## ADR-021: Negative Stock Is Absolutely Prohibited
- **Resolves:** CR-034.
- **Context:** A legitimate negative `INCOMING_RECONCILIATION`, a receiving reversal, or a negative `PHYSICAL_ADJUSTMENT` could each drive a balance below zero when the stock has since been issued, violating `CHECK (quantity >= 0)`.
- **Decision:** The non-negative constraint is absolute and is never relaxed, not even transiently within a transaction. Any operation that would breach it fails atomically with `INSUFFICIENT_STOCK` and a specific Arabic message naming the item and warehouse. The business resolution is an approved physical stock count, which establishes reality rather than papering over it.
- **Consequences:** The database check constraint is the last line of defence behind the conditional `UPDATE`. Both are retained.

## ADR-022: Optimistic Concurrency Uses PostgreSQL `xmin`
- **Resolves:** CR-035.
- **Context:** `06` declared `stock_balances.version BYTEA NOT NULL`. This is a SQL Server idiom; PostgreSQL has no auto-maintained `rowversion`. A `BYTEA` column would require manual maintenance and would **silently fail to detect lost updates** — a concurrency bug that passes every test written against a single-threaded suite.
- **Decision:** Drop the `version` column. Map the PostgreSQL `xmin` system column as the concurrency token via `.IsRowVersion()` / `UseXminAsConcurrencyToken()`. Retain the conditional atomic `UPDATE … WHERE quantity >= @qty` as the primary guard; `xmin` protects the WAC recomputation read-modify-write.
- **Consequences:** `06` and `29` corrected. A concurrency integration test asserting a detected conflict is mandatory in Phase 7.

## ADR-023: Base Units and Used Conversions Are Immutable
- **Resolves:** CR-037, CR-038, CR-039.
- **Context:** Editing an item's `base_unit_id` or a conversion factor after transactions exist would retroactively corrupt every normalized historical quantity in the ledger — silently, and irreversibly.
- **Decision:**
  - `items.base_unit_id` is immutable once any `stock_ledger` row exists for that item.
  - An `item_unit_conversions` row is immutable once referenced by any posted document. A corrected factor is a **new row**; the old row is deactivated and retained for historical resolution.
  - `item_unit_conversions.to_base_unit_id` must equal `items.base_unit_id`, enforced by composite foreign key and server validation.
- **Consequences:** Historical quantities remain reproducible. The item edit form disables the base-unit field once transactions exist, with an Arabic explanation.

## ADR-024: Sequence Periods Follow the Tenant Timezone
- **Resolves:** CR-052.
- **Context:** Monthly document numbers (`REC-YYYYMM-0000`) reset on a month boundary, but no document said in which timezone. `Africa/Cairo` and UTC disagree for three hours daily, so a UTC-derived period would place late-evening documents into the following month.
- **Decision:** The sequence period is derived from the document's **business date in the tenant's configured timezone**, defaulting to `Africa/Cairo`. All storage and transport remain UTC.
- **Consequences:** Document numbers match the business day a user would name. Documented in `docs/28`.

## ADR-025: Gap-Free Document Numbering via Transactional Counter Rows
- **Resolves:** CR-050, CR-053.
- **Context:** `04 §5` mandated a `tenant_sequences` table that does not exist in the schema, and never stated behaviour on rollback. A PostgreSQL `SEQUENCE` does not roll back and would leave gaps; auditors read a gap in a numbered document series as a deleted record.
- **Decision:** A `document_sequences` counter table is allocated **inside the business transaction** via `UPDATE … RETURNING`, so a rollback releases the number. Numbering is gap-free and monotonic per `(company_id, document_type, period)`. `SELECT MAX(...) + 1` remains strictly forbidden.
- **Consequences:** Writers serialize on one row per company per document type per month — acceptable at the target scale, and correct where a bare sequence would not be. Full specification in `docs/28`.

## ADR-026: OTP Rate Limiting Applies Both Windows
- **Resolves:** CR-060.
- **Context:** `08` stated the OTP limit twice and incompatibly: "3 per mobile per hour" in prose, "3 per IP/Mobile per 15 minutes" in the policy table.
- **Decision:** Both windows apply simultaneously and independently: **3 requests per mobile per 15 minutes** and **5 requests per mobile per hour**, plus the per-IP limit. Whichever triggers first returns `429 RATE_LIMIT_EXCEEDED`.
- **Consequences:** Burst abuse and slow enumeration are both bounded. `08 §2` and `08 §5` reconciled to this single statement.

The installed toolchain was verified by direct filesystem inspection and recorded in **`docs/33-verified-environment-matrix.md`**.

None of these transfers.
  - **Phase 2 is blocked until PostgreSQL 16+ is installed.** Phase 1 is unblocked and may proceed now, because it creates no schema.
  - Phase 1 pins the SDK in `global.json` (two .NET 10 SDKs are installed) and re-verifies every value by executing the commands in `docs/33 §6`.

## ADR-028: One Default Serving Warehouse Per Restaurant, Derived Server-Side
- **Closes:** OD-008. **Resolves:** CR-026.
- **Context:** `supply_requests.warehouse_id` was `NOT NULL`, but no document stated whether the Restaurant Supervisor chose the warehouse or the server derived it. A client-selected warehouse is both a usability burden on a branch user and an authorization hazard: a supervisor could redirect a requisition to any warehouse in the company by editing the request payload.
- **Decision:** Each `Restaurant` has **exactly one** default Serving Warehouse (`restaurants.default_serving_warehouse_id`, `NOT NULL`) in the initial product version. The Restaurant Supervisor **never** selects a warehouse. The backend derives it from the restaurant's configured default.
  - The supply-request creation DTO **does not declare a `warehouseId` property**, so an over-posted value is discarded by the model binder rather than merely ignored by the handler.
  - The derived warehouse must belong to the **same company** as the restaurant (guaranteed structurally by the composite tenant foreign key of ADR-016) and must be `status = 'Active'`.
  - If the restaurant has no active serving warehouse, creation fails with `409 SERVING_WAREHOUSE_UNAVAILABLE` (`"لا يوجد مستودع خدمة مفعّل لهذا الفرع، يرجى مراجعة إدارة النظام"`). The server never falls back to "any warehouse".
  - Configuring a restaurant's serving warehouse is master data, restricted to `Owner` and `Admin` via `restaurants:manage`, and is audited.
  - Warehouse Staff authorization is unchanged: a staff member sees and processes only requests whose derived warehouse is inside their `UserWarehouseScope`.
- **Consequences:** A Restaurant Supervisor cannot redirect a request to another warehouse by any API path, because there is no input to manipulate. The one-warehouse-per-restaurant constraint is a deliberate v1.0 simplification; a future many-to-many `restaurant_serving_warehouses` mapping with a selection rule is a version increment, not a patch.

## ADR-029: Files and Reports Deferred; Reportability Preserved
- **Closes:** OD-011.
- **Context:** `16-files-evidence.md` and `17-reporting.md` were fully specified, but neither is required by any approved core workflow. Building a generic file subsystem and a reporting engine before the inventory core is complete would consume the phases where correctness matters most.
- **Decision:**
  - **Files — deferred.** No generic file-management subsystem is built. File storage enters scope only when an *already-approved* workflow explicitly requires an attachment. No approved workflow currently does: receiving, supply requests, fulfilment, dispatch, confirmation, discrepancies, consumption, and stock counts all complete without one. `16-files-evidence.md` remains a valid future specification and is marked **DEFERRED — NOT IN MVP SCOPE**.
  - **Reports — deferred as implementation, preserved as capability.** No report endpoint, no export pipeline, no `/reports` route, and — emphatically — **no placeholder charts, no fake KPIs, no mock report screens**. What *is* required now is that the core data remain reportable: the append-only `stock_ledger` retains actor, movement type, reference, cost, and timestamp on every row; `audit_logs` retains full actor and diff context; documents retain their line-level links; and the indexes of `docs/29 §5` already cover the aggregation paths future reports will use. Reporting extension points are documented in `17-reporting.md`.
- **Consequences:** Phases 15 and 16 move to a post-core position and block nothing. `docs/12`'s Owner navigation retains a `التقارير` entry as a **future** item that is not rendered until the reports phase ships — an unimplemented route is never shown as an empty or placeholder screen. Deferral is explicitly **not** deletion: both specifications survive intact so that the later phases start from a written baseline rather than a fresh guess.

## ADR-031: End-to-End Tests Live in the Frontend as `@playwright/test`
- **Resolves:** CR-096.
- **Context:** `docs/18 §1` placed the E2E suite at `tests/Inventory.E2E/` as a **.NET** Playwright project, while `docs/09 §8` specified `npm run test:e2e --prefix frontend` — a **Node** Playwright project. Both statements were current and authoritative, and they cannot both be built without producing two partially maintained E2E suites that drift apart.
- **Decision:** The E2E suite is **`@playwright/test` in the frontend**, at `frontend/e2e/`, run by `npm run test:e2e --prefix frontend`. `tests/Inventory.E2E/` is **not** created.
- **Rationale:** E2E tests drive the browser UI, so they belong in the language and toolchain of the application they drive. The Node runner gives the tooling the .NET binding lacks — trace viewer, UI mode, codegen — and the assertions are written by the same people who write the components. It also removes a second Playwright browser installation from CI. The Arabic RTL, export, and accessibility checks of `docs/31 §9` are DOM assertions, which is exactly what this runner is for.
- **Consequences:** The .NET test solution is three projects — `Inventory.UnitTests`, `Inventory.IntegrationTests`, `Inventory.ArchitectureTests`. `docs/18 §1` is corrected. `docs/09 §8` was already right and is unchanged. API-level integration tests remain in .NET via `WebApplicationFactory`; only browser-level tests move.
